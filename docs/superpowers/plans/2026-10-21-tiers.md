# Plans and tiers (Phase 4): implementation plan + dashboard checklist

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (controller) / superpowers:test-driven-development (each worker). Part (a) is code for two parallel workers. Part (b) is dashboard work the **controller** does itself; workers never touch dashboards.

**Goal:** three plans in one App Store subscription group: Website, Bookings and Store. The server opens the booking page only on the Bookings or Store plan, and the shop page only on the Store plan. A downgrade pauses the page it no longer covers, and a lapse of the whole subscription takes everything down (Phase 2 lapse). The app shows the `bookings_upgrade` / `store_upgrade` paywalls on those tabs, and the publish paywall keeps selling only the Website plan.

**Spec:** §3 (lapse), §5, §7, §11 of `docs/superpowers/specs/2026-10-21-bookings-store-design.md`.

**Depends on:** Phase 3 being merged (server `store-integration` on main, app `app` with Store tab), because this phase edits `storeOpen` and the Store tab.

## Binding rulings (controller, 2026-10-21)

### Product to entitlement map

This lives in one place on the server, `lib/ios/tiers.ts`, and is mirrored in Superwall and RevenueCat.

| Product id prefix | Tier | Entitlements |
|---|---|---|
| `com.ibrahim1774.aibarber.hosting.` (`.monthly`, `.yearly`) | `website` | `hosting` |
| `com.ibrahim1774.aibarber.bookings.` (`.monthly`, `.yearly`) | `bookings` | `hosting`, `bookings` |
| `com.ibrahim1774.aibarber.store.` (`.monthly`, `.yearly`) | `store` | `hosting`, `bookings`, `store` |

- `IOS_PRODUCT_IDS` lists exactly these six ids.
- An unknown id still returns `bad-product`.

### Upgrades and downgrades

- All three tiers share subscription group 22497224 and keep the same `originalTransactionId`. The shop's `ab_shops.ios_otid` therefore never changes on an upgrade or downgrade.
- **Upgrades take effect immediately. Downgrades take effect at the next renewal.** Both are Apple-native.

### The current product is the latest transaction's product

- Today `makeVerifier` returns the product of the transaction id the app sent, which can be the first period's. Phase 4 returns `latest.productId` and `latest.purchaseDate`.
- `ios_purchases.product_id` never moves backwards. It is written only when the transaction's purchase date is ≥ the stored `product_purchased_at` (migration 010), the same never-backwards rule as `expires_at`.
- **A transaction with `isUpgraded === true` is the upgraded-away one.** Its `revocationDate` never sets `revoked_at`, and its product is never written.

### Gates (server is authoritative)

- **Booking page** (`bookingsOpen`): the Phase 2 rule **and** the linked purchase grants `bookings`.
- **Shop page** (`storeOpen`): the Phase 3 rule **and** the linked purchase grants `store`.
- **Owner bookings writes:**
  - Gated: walk-in create, owner reschedule and time-off. They return `423 bookings-paused` unless `ios_otid` is set, the purchase is not revoked or taken down, and it grants `bookings`.
  - Never gated: owner cancel (refunds customers) and `mark` (finishing existing bookings).
- **Owner order actions:** never gated. Orders already placed must stay fulfillable and refundable after a downgrade, and "orders remain visible" (§11).
- **`/api/shop/setup`:** never gated, because it is how a purchase gets linked.

### Lapse rules (§11)

| What lapsed | Server | App |
|---|---|---|
| `hosting` (whole subscription inactive) | The Phase 2 sweep takes the site offline (`taken_down_at`). That alone pauses the booking page and closes the shop, because both gates check `taken_down_at` and `revoked_at`. | Edit tab LapsedCard (exists). Bookings and Store are read-only for 30 days after `expiresAt`, then show the upgrade card. |
| `bookings` (downgraded to Website) | Booking page paused (gate); owner bookings writes return 423; Book buttons stripped on the next publish. | Bookings tab: calendar read-only + "Your booking page is paused" banner with **Upgrade**. |
| `store` (downgraded to Website or Bookings) | Shop page closed (gate); `shopUrl` stripped on the next publish. Orders stay visible and actionable. | Store tab: products and orders read-only (order actions stay available) + "Your shop page is offline" banner with **Upgrade**. |

### Book and Shop links on the website

These are stripped **server-side** in `runIosPublish`, so old app builds can't bypass it:

- `bookingUrl` is removed when it is an AI Barber booking link (`^https?://(www\.)?aibarber\.org/book/`, case-insensitive) and the verified product lacks `bookings`. A Booksy or Square link is never touched.
- `shopUrl` is removed when the product lacks `store`.

The app applies the same rule before rendering and publishing, so the preview matches.

### RevenueCat

- RevenueCat stays an observer: it makes no purchases and has no offerings in the app.
- Its products and entitlements mirror the table above. No app code reads RevenueCat entitlements.

### The publish paywall

- The publish paywall (Superwall 283009, placement `publish`) keeps **only** the two Website products.
- A Bookings or Store subscriber has the `hosting` entitlement, so publishing never shows a paywall to them.

### Upgrade paywall settle

- For `bookings_upgrade` and `store_upgrade`, "paid" means **the target entitlement is now active**, not "a transaction exists", which is always true for an existing subscriber.
- A dismiss without that entitlement is `declined`.

### Prices

- Never show a monthly-equivalent price for a yearly product on any paywall or screen.
- Yearly prices are shown as "$X/yr · Billed yearly".

### `/api/shop/plan` contract (T-S produces, T-A consumes)

Owner only: `Authorization: Bearer <Supabase access token>`.

**`GET /api/shop/plan`** returns `200` with:

```
{ linked: boolean, tier: 'website'|'bookings'|'store'|null,
  entitlements: { hosting: boolean, bookings: boolean, store: boolean },
  active: boolean, expiresAt: string|null, takenDownAt: string|null, revoked: boolean }
```

- `active` means not revoked and not taken down.
- `entitlements.*` is false when not active.
- `linked: false` (no `ios_otid`) gives `tier: null` and all entitlements false.
- `404 no-shop`.

**`POST /api/shop/plan`**

- Body: `{ transactionId }`. The app calls it right after an upgrade purchase.
- It verifies with Apple (the latest product), runs `upsertVerified`, links `ios_otid` if the shop has none (the same rules and `409 purchase-in-use` as setup), and returns the GET body.
- Errors: `400 invalid` (bad id or `bad-product`), `503 temporarily-unavailable` (Apple).
